# Contributing

Thanks for looking. This is a small tool with a deliberately narrow scope, so
the most useful thing to know up front is what it will and will not become.

## Setup

**Development needs Node 20 or newer** — Vitest 4 requires it.

The published package supports **Node 18+**, which is a separate claim: nothing
in the dev toolchain ships to a consumer. CI enforces both, and the split is
deliberate. The `runtime` job installs the packed tarball with
`--omit=dev` and runs the binary on 18, 20, 22 and 24; the `test` job runs the
toolchain on 20+.

```bash
npm install
npm run check     # typecheck + tests
npm run build
npm run demo      # regenerates docs/demo.svg
```

## The two fixtures that define correctness

Everything hinges on these:

- The **Wong palette** (published as CVD-safe) must never fail.
- The **RudeSync palette** (known bad) must fail.

If a change breaks either, the thresholds are wrong and nothing else about the
change matters. Both are pinned in `test/check.test.ts`, along with the
sensitivity window around `FAIL_RATIO`.

## Numbers must be derived, not typed

The pass floors are computed from the Wong palette at load, so they cannot drift
away from the simulation model. Please keep it that way — a hardcoded constant
that happens to match today is a constant that silently stops matching later.

The same applies to anything published: `docs/demo.svg` is generated by a script
that asks the library for the simulated colours. An image tinted by hand would
be an illustration; this one is a measurement, and that difference is the reason
anyone should believe it.

## Scope

**In:** categorical palettes, CVD distinguishability, better reporting, more
input formats, integrations that let other tools depend on the core.

**Out, deliberately:**

- **WCAG contrast checking.** A different failure mode, and already well served
  by existing tools. Staying out of it is the positioning, not an oversight.
- **Suggesting replacement colours.** A much harder problem; other tools
  generate palettes.
- **General design-token linting.** A linter cannot know which tokens are used
  together, so all-pairs checking over a token file is mostly false positives.
  This tool works precisely because a categorical palette *is* a set of colours
  meant to be mutually distinguishable. Widening the input undoes that.
- **Sequential and diverging palettes.** Different maths, different rules.

If you want one of these, an issue is welcome — but expect the answer to be a
pointer to a tool that already does it.

## Claims

Please do not add language claiming the tool delivers WCAG compliance. It does
not: WCAG 1.4.1 asks that colour not be the *only* carrier of meaning, and its
remedy is labels and patterns as much as colour choice. Fixing a palette is
necessary, not sufficient. `docs/audit.md` sets out where that line sits.

## Commits

Small and focused. Say what changed and why; the why is the part that is hard to
recover later.
